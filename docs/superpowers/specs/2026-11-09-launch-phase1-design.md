# เฟส 1: ระบบสำหรับ launch บน Cloudflare

- **วันที่:** 2026-11-09
- **สถานะ:** รอรีวิวสเปก
- **ขอบเขต:** backend, ระบบบัญชีและ login, การแยกข้อมูลแต่ละร้าน, ขายตอนออฟไลน์แล้ว sync, ย้ายข้อมูลจาก localStorage, แพ็กเกจและเพดาน, ระบบเก็บเงินผ่าน Stripe, หลังบ้านทีม และงาน security ก่อนเปิดใช้จริง

## เป้าหมาย

ให้ร้านจริงสมัคร ใช้งาน และจ่ายค่าแพ็กเกจได้เองโดยไม่ต้องมีทีมช่วย บน Cloudflare โดยให้ security มาก่อนความสะดวกของฝั่งพัฒนา

**เกณฑ์สำเร็จ**

1. ร้านสมัคร login และขายได้ทั้งตอนออนไลน์และตอนเน็ตหลุด บิลที่ออกตอนออฟไลน์ถึง server ครบเมื่อเน็ตกลับมา ไม่หายและไม่ซ้ำ
2. ร้านหนึ่งอ่านหรือแก้ข้อมูลของร้านอื่นไม่ได้ และมีเทสต์อัตโนมัติยืนยันกับทุก endpoint
3. เพดานแพ็กเกจและสิทธิ์พนักงานบังคับที่ server
4. ข้อมูลร้านไม่หายเมื่อล้างเบราว์เซอร์ เปลี่ยนเครื่อง หรือเครื่องหาย
5. ราคา เพดาน และฟีเจอร์ของแพ็กเกจแก้จากหลังบ้านได้โดยไม่ต้อง deploy
6. launch ได้ก่อนบัญชี Stripe จะ activate

## 1. ภาพรวมระบบ

### โดเมน

| โดเมน | ให้บริการ |
|---|---|
| โดเมนหลัก | แลนดิ้ง (ไฟล์ static ย้ายจาก Vercel) |
| `app.` | ตัวแอปและ API ที่ `/api/v1/*` อยู่ origin เดียวกัน cookie เป็น first-party และไม่เปิด CORS |
| `admin.` | หลังบ้านทีม อยู่หลัง Cloudflare Access |

ชื่อโดเมนจริงกำหนดใน `wrangler.toml` ของแต่ละ environment

### ชิ้นส่วนฝั่ง server

| ชิ้น | หน้าที่ |
|---|---|
| Worker `api` (TypeScript + Hono) | รับ request, ตรวจ session หรือ device token, auth, webhook ของ Stripe แล้วส่งคำสั่งต่อไปที่ Durable Object ของร้าน **ร้านเป้าหมายมาจาก session เสมอ ไม่รับจาก client** |
| Durable Object `Shop` (ร้านละตัว เก็บใน SQLite) | เจ้าของข้อมูลร้านทั้งหมด ทำคำสั่งทีละรายการ บังคับสิทธิ์และเพดาน ตั้ง `locationHint: 'apac'` |
| D1 `core` | ผู้ใช้, ช่องทาง login, session, ร้าน, สมาชิกร้าน, เครื่อง, รหัส OTP, แพ็กเกจ, subscription, event ของ Stripe, ข้อตกลงที่ยอมรับ |
| R2 `media` | รูปสินค้าและโลโก้ |
| R2 `backups` | ไฟล์ backup รายวัน ล็อกห้ามลบ 90 วัน |
| Queues `outbound` | ส่งอีเมลและ SMS |
| Cron | backup รายวัน, ปิดแพ็กเกจที่เลยระยะผ่อนผัน, ล้าง session และ OTP ที่หมดอายุ, ลบร้านที่พ้นระยะ 30 วัน |

### ฝั่งแอป

| ไฟล์ | หน้าที่ |
|---|---|
| `store.js` (ใหม่) | เก็บข้อมูลร้านใน IndexedDB และมีคิวคำสั่งที่รอส่ง (outbox) `app.js` เรียกคำสั่งผ่านโมดูลนี้แทนการเขียน `state` ลง localStorage |
| `sync.js` (ใหม่) | ส่ง outbox ขึ้น server รับการเปลี่ยนแปลงลงมา และบอกสถานะออนไลน์หรือออฟไลน์ให้หน้าจอ |
| `sw.js` (ใหม่) | service worker เก็บไฟล์แอปและรูปไว้ให้เปิดได้ตอนออฟไลน์ |
| `auth.js` และหน้า login (ใหม่) | login, เลือกร้าน, ใส่ PIN, ลงทะเบียนเครื่อง |
| `app.js`, `settings.js` | ยังเป็นตัวจัดการหน้าจอ แต่เปลี่ยนการบันทึกเป็นการส่งคำสั่งทีละรายการ เช่น `sale.create`, `stock.restock` |

### ทางของข้อมูลเมื่อออกบิล

1. แอปบันทึกบิลลง IndexedDB และใส่คำสั่งเข้า outbox ทันที (ใช้ได้ทั้งออนไลน์และออฟไลน์)
2. `sync.js` ส่งคำสั่งเป็นชุดไปที่ `POST /api/v1/sync`
3. Worker ตรวจ session หรือ device token แล้วส่งต่อให้ Durable Object ของร้านนั้นพร้อมเพดานแพ็กเกจปัจจุบัน
4. Durable Object ทำทีละคำสั่งตามลำดับ ตัดสต็อก บันทึก log แล้วตอบผลกับการเปลี่ยนแปลงล่าสุด
5. เครื่องอื่นในร้านได้รับการเปลี่ยนแปลงในรอบ sync ถัดไป

## 2. Auth, session, เครื่อง และ PIN พนักงาน

### บัญชีและช่องทาง login

ผู้ใช้หนึ่งคน (`users`) มีหลายช่องทาง login (`identities`: `provider`, `subject`) คู่ provider กับ subject ซ้ำกันไม่ได้

| ช่องทาง | ข้อกำหนด |
|---|---|
| LINE | OIDC + PKCE + `state` + `nonce` ตรวจ `id_token` ที่ server |
| Google | OIDC + PKCE ตรวจลายเซ็นจาก JWKS และตรวจ `aud`, `iss`, `exp` |
| OTP อีเมล | 6 หลัก หมดอายุ 10 นาที ใช้ครั้งเดียว ผิดได้ 5 ครั้ง เก็บเป็น HMAC-SHA256 กับ secret ฝั่ง server |
| OTP เบอร์โทร | กฎเดียวกับอีเมล รับเฉพาะเบอร์ไทย (+66) เก็บเป็นรูปแบบ E.164 มีเพดานค่า SMS ต่อวันและแจ้งเตือนเมื่อถึง 80% |

- หน้าขอ OTP ทุกหน้ามี Turnstile และจำกัดความถี่ทั้งต่อปลายทาง (อีเมลหรือเบอร์) และต่อ IP
- ข้อความตอบกลับเหมือนกันไม่ว่าจะมีบัญชีหรือไม่

### การผูกบัญชี

- **ไม่รวมบัญชีอัตโนมัติ** แม้อีเมลหรือเบอร์จะตรงกัน login ด้วยช่องทางที่ยังไม่ผูกจะสร้างบัญชีใหม่เสมอ
- ผูกช่องทางเพิ่มได้จากหน้าตั้งค่าเท่านั้น ต้อง login อยู่และยืนยันช่องทางใหม่สำเร็จ
- ถอดช่องทางได้ถ้ายังเหลืออย่างน้อยหนึ่งช่องทาง

### Session ของเจ้าของ

- token สุ่ม 256 บิต D1 เก็บเฉพาะค่า SHA-256
- cookie `__Host-kn_s` ตั้ง `HttpOnly; Secure; SameSite=Lax; Path=/`
- อยู่ได้ 30 วันนับจากใช้ครั้งล่าสุด และไม่เกิน 90 วันนับจาก login
- ออก token ใหม่ทุกครั้งที่ login และมีหน้าออกจากระบบทุกเครื่อง
- **กัน CSRF:** คำขอที่ไม่ใช่ `GET` ต้องมี `Origin` ตรงกับ `app.` และมี header `X-Khonnai: 1`
- **งานที่ต้อง login ภายใน 10 นาทีที่ผ่านมา:** จ่ายเงินหรือเปลี่ยนแพ็กเกจ, เพิ่มหรือลบพนักงาน, ลงทะเบียนหรือถอดเครื่อง, ส่งออกข้อมูล, ผูกหรือถอดช่องทาง login, ลบร้าน, ลบบัญชี

### ร้าน บทบาท และพนักงาน

- บทบาทมี `owner` กับ `staff` ผู้ใช้หนึ่งคนเป็นเจ้าของได้หลายร้าน (`memberships`)
- **พนักงานไม่ใช่ผู้ใช้:** เป็นโปรไฟล์ในร้าน มีชื่อ, ค่า hash ของ PIN และสถานะ เก็บใน Durable Object ของร้าน

| งาน | owner | staff |
|---|---|---|
| ขาย จอง รับของจากใบจอง | ✓ | ✓ |
| ใส่ส่วนลดในบิลหรือใบจอง | ✓ | – |
| ดูสต็อก เติมสต็อกของรุ่นที่มีอยู่แล้ว | ✓ | ✓ |
| เพิ่มรุ่นใหม่ อัปโหลดรูป | ✓ | – |
| ยกเลิกบิล แก้ราคา ลบหรือซ่อนสินค้า ปรับสต็อกเป็นค่าที่กำหนด | ✓ | – |
| ดูยอดรวมและรายงาน | ✓ | – |
| แก้ตั้งค่า จัดการพนักงานและเครื่อง ส่งออกข้อมูล เรื่องเงิน | ✓ | – |

สิทธิ์ตรวจที่ Durable Object ทุกคำสั่ง แอปแค่ซ่อนปุ่ม ยกเว้นบิลจากพนักงานที่มีส่วนลดซึ่งออกตอนออฟไลน์: รับไว้เพราะขายไปแล้ว และติดธง `staff_discount` ให้เจ้าของตรวจ (หน้าจอของพนักงานไม่มีช่องส่วนลด กรณีนี้จึงเกิดได้เฉพาะเมื่อแอปถูกแก้)

### เครื่องร้าน

- เจ้าของที่ login อยู่กด "ตั้งเป็นเครื่องร้าน" → server ออก device token แยกจาก session เจ้าของ ใช้ได้กับร้านเดียว สิทธิ์สูงสุดเท่าพนักงาน และได้รหัสเครื่อง (`A`, `B`, ...) ไว้ใช้ในเลขบิล
- cookie `__Host-kn_d` ตั้งค่าเหมือน session
- เปลี่ยน token ใหม่เมื่อ sync สำเร็จวันละครั้ง token ก่อนหน้ายังใช้ได้อีก 7 วัน
- เจ้าของดูรายชื่อเครื่องพร้อมเวลาที่เห็นล่าสุด และถอดได้ทันที

### PIN พนักงาน

- 6 หลัก
- **ตอนออนไลน์:** ตรวจที่ server ผิด 5 ครั้งล็อก 5 นาที แล้วเพิ่มเป็นสองเท่าทุกรอบ
- **ตอนออฟไลน์:** เครื่องเก็บค่า PBKDF2-SHA256 แบบใส่ salt ไว้ตรวจเอง
- **ข้อจำกัดที่ยอมรับ:** PIN เป็นแค่ประตูสลับคนบนเครื่อง ไม่ใช่กำแพงกันขโมย คนที่ได้เครื่องไปเดา PIN ตอนออฟไลน์ได้ ของที่กันจริงคือ device token กับการที่เจ้าของถอดเครื่องได้
- ทุกคำสั่งบันทึกว่าพนักงานคนไหนเป็นคนทำ
- เจ้าของใช้งานบนเครื่องร้านได้ด้วยการ login เต็ม ไม่มี PIN เจ้าของ

### Audit log ของระบบ auth

บันทึกใน D1: login สำเร็จและไม่สำเร็จ, ผูกหรือถอดช่องทาง, ลงทะเบียนหรือถอดเครื่อง, เปลี่ยน PIN, ลบบัญชี ไม่เก็บ token หรือรหัส OTP

## 3. ข้อมูลร้าน, sync ตอนออฟไลน์ และการย้ายข้อมูลเดิม

### ตารางใน Durable Object `Shop`

เงินทุกช่องเก็บเป็นจำนวนเต็มหน่วยสตางค์

| ตาราง | เก็บอะไร |
|---|---|
| `products` | รหัส (key), ชื่อ, หมวด, ราคา, จำนวนต่อแพ็ก, key รูป, สถานะเปิดขาย ลบแบบซ่อน ไม่ลบจริง |
| `price_history` | ราคาย้อนหลังพร้อมเวลาที่เริ่มใช้ |
| `variants` | สต็อกแยกสีและไซซ์ สินค้าที่ไม่แยกมีแถวเดียว (สี "ทั้งหมด" ไซซ์ "รวม") |
| `stock_moves` | สมุดบัญชีสต็อก: จำนวนที่เปลี่ยน, เหตุผล (`sale`, `void`, `reserve`, `unreserve`, `restock`, `adjust`), อ้างอิง, พนักงาน, เวลา |
| `sales`, `sale_lines` | บิลกับรายการในบิล รายการเก็บราคาต่อหน่วย ณ ตอนขาย บิลมีสถานะ `active` หรือ `voided` ลบไม่ได้ |
| `reservations`, `reservation_lines` | ใบจอง สถานะ `waiting`, `fulfilled`, `cancelled` |
| `customers` | ลูกค้าของร้าน |
| `staff` | พนักงาน |
| `settings` | ตั้งค่าร้านเป็น key/value: ข้อมูลร้าน, PromptPay, หมวด, สี, เกณฑ์สต็อกใกล้หมด |
| `ops` | `seq`, `op_id` (ห้ามซ้ำ), เครื่อง, พนักงาน, ชนิด, payload, ผลลัพธ์, ธง, เวลา ใช้กันบันทึกซ้ำและใช้เป็น audit log ของร้าน |
| `changes` | `seq` → ตารางกับ id ของแถวที่เปลี่ยน เก็บ 30 วัน |

`variants.qty` คือผลรวมของ `stock_moves` และอัปเดตใน transaction เดียวกัน

**เลขบิล:** รหัสเครื่องตามด้วยเลขนับของเครื่องนั้น เช่น `A-000123` เครื่องออกเลขเองได้แม้ออฟไลน์

### คำสั่งที่ทำตอนออฟไลน์ได้

| ออฟไลน์ได้ | ต้องออนไลน์ |
|---|---|
| `sale.create` | `sale.void` |
| `stock.restock` (บวกเพิ่มอย่างเดียว) | `product.*`, `stock.adjust` |
| | `reservation.*` |
| | `settings.*`, `staff.*`, `device.*` |

ปุ่มของคำสั่งที่ต้องออนไลน์จะปิดไว้ตอนเน็ตหลุดและบอกเหตุผล

### การ sync

1. ทุกคำสั่งมี `op_id` เป็น UUID ที่เครื่องสร้าง เข้า outbox ก่อนเสมอ
2. `POST /api/v1/sync` ส่ง `{cursor, ops[]}` ได้ไม่เกิน 100 คำสั่งต่อครั้ง
3. ส่งเมื่อ: หลังทำรายการ (ถ้าออนไลน์), เมื่อเน็ตกลับมา, ทุก 30 วินาทีขณะเปิดหน้าแอปอยู่, ตอนเปิดแอป
4. Durable Object ทำทีละคำสั่งใน transaction:
   - ถ้า `op_id` เคยทำแล้ว ตอบผลเดิม
   - ถ้ายังไม่เคย ตรวจ schema → สิทธิ์ → เพดาน แล้วทำคำสั่ง และบันทึกลง `ops` กับ `changes`
5. คำตอบมี `results[]` (`applied` หรือ `rejected` พร้อมเหตุผล), แถวล่าสุดของทุกแถวที่เปลี่ยนหลัง `cursor` และ `cursor` ใหม่
6. ส่งกลับเป็นสถานะของแถว ไม่ใช่ให้เครื่องทำคำสั่งซ้ำ ตรรกะธุรกิจจึงอยู่ที่ server ที่เดียว
7. ถ้า `cursor` เก่ากว่าข้อมูลใน `changes` server ส่งข้อมูลทั้งชุดที่เครื่องนั้นควรมี
8. คำสั่งที่ต้องออนไลน์ส่งผ่าน `/api/v1/sync` เหมือนกัน แต่หน้าจอรอผลก่อนแสดงว่าสำเร็จ
9. **`sale.create` มีสองโหมด:**
   - **ออนไลน์:** ส่งทันทีพร้อม `mode: "online"` แล้วหน้าจอรอผลไม่เกิน 5 วินาทีก่อนแสดงบิล ถ้าสต็อกไม่พอ server ปฏิเสธด้วย `insufficient_stock` พร้อมจำนวนคงเหลือล่าสุด และหน้าจอให้แก้จำนวน
   - **ออฟไลน์:** ถ้าเครื่องออฟไลน์อยู่ หรือส่งแล้วไม่ได้คำตอบใน 5 วินาที บันทึกเข้า outbox ด้วย `mode: "offline"` และแสดงบิลทันที
   - การปฏิเสธด้วย `insufficient_stock` ในโหมดออนไลน์ไม่บันทึกลง `ops` เป็นผลสุดท้าย ถ้าคำตอบมาไม่ทันแล้วคำสั่งเดิม (`op_id` เดิม) ถูกส่งซ้ำในโหมดออฟไลน์ จะประเมินใหม่ตามกฎออฟไลน์ บิลที่หน้าจอแสดงไปแล้วจึงไม่ถูกปฏิเสธทีหลัง
   - ฝั่งแอปตรวจสต็อกจากข้อมูลในเครื่องก่อนทั้งสองโหมด
   - ถ้าแอปถูกแก้ให้ส่ง `offline` แทน `online` ผลคือได้สต็อกติดลบพร้อมธงเหมือนกรณีออฟไลน์จริง ไม่ได้ข้ามการตรวจอื่น

### เมื่อข้อมูลชนกัน

| กรณี | ทำอย่างไร |
|---|---|
| ขายเกินสต็อก โหมดออนไลน์ | ปฏิเสธด้วย `insufficient_stock` |
| ขายเกินสต็อก โหมดออฟไลน์ (เช่น สองเครื่องขายชิ้นสุดท้าย) | รับบิล สต็อกติดลบได้ ติดธง `negative_stock` และขึ้นรายการ "สต็อกติดลบ" ที่หน้าโฮมเจ้าของ |
| ราคาในบิลไม่ตรงราคาปัจจุบัน | รับถ้าตรงกับราคาใน `price_history` ภายใน 7 วัน ถ้าไม่ตรง รับไว้และติดธง `price_mismatch` ให้เจ้าของตรวจ |
| สินค้าถูกซ่อนระหว่างที่เครื่องออฟไลน์ | รับบิลตามปกติ |
| เกินเพดานบิลรายเดือนตอนออฟไลน์ | รับบิลที่ขายไปแล้วและติดธง `over_limit` คำสั่ง `sale.create` ที่ส่งขณะออนไลน์หลังเกินเพดานจะถูกปฏิเสธ |
| เวลาบนเครื่องเพี้ยน | ใช้เวลาเครื่องถ้าไม่อยู่ในอนาคตเกิน 5 นาทีและไม่ย้อนหลังเกิน 30 วัน ถ้าเกิน ใช้เวลาที่ server รับและติดธง `clock_skew` |
| คำสั่งถูกปฏิเสธ | ขึ้นเป็น "รายการที่ส่งไม่สำเร็จ" บนเครื่องและในหน้าของเจ้าของ ไม่ลบเงียบ |

### ข้อมูลที่เก็บในเครื่อง

- **เครื่องร้าน:** สินค้า, สต็อก, ลูกค้า, ใบจองที่ยังเปิด, บิล 2 วันล่าสุด, ค่า hash ของ PIN พนักงาน, เพดานแพ็กเกจ
- **เครื่องเจ้าของ:** ข้อมูลร้านทั้งหมด
- **ข้อจำกัดที่ยอมรับ:** IndexedDB ไม่ได้เข้ารหัส การซ่อนยอดรวมของบิล 2 วันล่าสุดจากพนักงานเป็นแค่ระดับหน้าจอ
- เมื่อ server ตอบว่าเครื่องถูกถอดหรือ session หมดอายุ แอปล้างข้อมูลร้านในเครื่อง (ทั้ง IndexedDB และ cache ของ service worker) แต่ถ้ายังมีคำสั่งใน outbox ที่ยังไม่ได้ส่ง ต้องเตือนก่อนล้าง

### รูปสินค้าและโลโก้

- `PUT /api/v1/images` เฉพาะเจ้าของ
- รับ JPEG, PNG และ WebP โดยตรวจจาก magic bytes ไม่เกิน 5 MB
- ใช้ Cloudflare Images ย่อเหลือด้านยาวสุด 800 px แปลงเป็น WebP และลบ metadata แล้วเก็บใน R2 `media` ด้วย key `shops/{shop_id}/{uuid}.webp`
- `GET /api/v1/images/{key}` ตรวจว่า key อยู่ใต้ร้านของ session ก่อนส่ง
- service worker cache รูปไว้ใช้ตอนออฟไลน์

### ย้ายข้อมูลจาก localStorage เดิม

1. login ครั้งแรกบนเครื่องที่มีค่า `khonnai-home-mvp-v3` แอปเสนอให้ย้ายข้อมูลเข้าร้าน
2. ฝั่งแอปแปลงข้อมูลให้ตรงรูปแบบใหม่ ไม่ย้ายข้อมูลที่แอปติดป้ายว่าเป็นตัวอย่าง (บิลและยอดตัวอย่างของต้นแบบ) รูปที่เป็น data URL อัปโหลดผ่าน `/api/v1/images` ทีละรูป
3. `POST /api/v1/import` รับได้เฉพาะเจ้าของ, เฉพาะร้านที่ยังไม่มีสินค้าหรือบิล, และครั้งเดียวต่อร้าน ตรวจทุกช่องด้วย schema เดียวกับคำสั่งปกติ
4. ข้อมูลที่ย้ายมาไม่ถูกตัดตามเพดาน ถ้าเกินเพดานของแพ็กเกจปัจจุบัน จะเพิ่มรายการใหม่ในหมวดที่เกินไม่ได้จนกว่าจะอัปเกรด
5. ย้ายสำเร็จแล้วเปลี่ยนชื่อค่าเดิมเป็น `khonnai-home-mvp-v3-backup` และลบเองหลัง 30 วัน

## 4. แพ็กเกจ, เพดาน, ระบบเก็บเงิน และหลังบ้าน

### แพ็กเกจเป็นข้อมูล

ตาราง `plans` และ `plan_versions` ใน D1 เป็นแหล่งเดียวของราคา เพดาน และฟีเจอร์ แต่ละเวอร์ชันมี:

```json
{
  "limits": { "skus": 200, "bills_per_month": 500, "staff": 3, "devices": 2 },
  "features": ["staff_pin", "reservations", "promptpay_qr"],
  "price_satang": 29900,
  "stripe_price_id": "price_...",
  "public": { "name": "Basic", "audience": "ร้านค้าส่งทั่วไป", "highlights": ["..."] }
}
```

- โค้ดเช็กด้วย `limit(shop, key)` และ `can(shop, feature)` ห้ามเช็กชื่อแพ็กเกจในโค้ด
- แก้และสร้างเวอร์ชันใหม่ได้จากหลังบ้าน ไม่ต้อง deploy
- แต่ละร้านจำว่าใช้เวอร์ชันไหน ร้านเดิมใช้ราคาเดิมต่อจนกว่าทีมจะย้ายโดยตั้งใจและแจ้งล่วงหน้า
- ข้อมูลตั้งต้นใน seed:

  | แพ็กเกจ | ราคา | สินค้า | บิล/เดือน |
  |---|---|---|---|
  | Free | 0 | 20 | 50 |
  | Basic | 299 บาท/เดือน | 200 | 500 |
  | Pro | 699 บาท/เดือน | 1,000 | 2,000 |

  ส่วนเพดานพนักงาน เพดานเครื่อง และรายการฟีเจอร์ของแต่ละแพ็กเกจ ทีมกำหนดในหลังบ้านก่อนเปิดร้านนำร่อง seed ตั้งให้ทุกแพ็กเกจได้ทุกฟีเจอร์ และพนักงานกับเครื่องไม่จำกัด

- `GET /api/v1/plans` เปิดสาธารณะ ส่งเฉพาะข้อมูลใน `public` กับราคาของเวอร์ชันปัจจุบัน แลนดิ้งและแอปอ่านจากที่นี่ แลนดิ้งฝังค่าที่ดึงได้ตอน build ไว้ใช้เมื่อ API ล่ม

### เปิดหรือปิดการเก็บเงิน

- ค่าตั้ง `BILLING_ENABLED` แยกต่อ environment
- **ปิด:** หน้าอัปเกรดแสดง "ติดต่อทีมทาง LINE" ทีมเปิดแพ็กเกจให้จากหลังบ้าน (ช่องทาง `comp` พร้อมวันหมดอายุ)
- **เปิด:** ใช้ Stripe ตามด้านล่าง
- staging ใช้ Stripe test mode ตลอด production เปิดเมื่อบัญชี Stripe activate แล้ว

### ช่องทางจ่ายเงิน (เมื่อเปิด)

| ช่องทาง | วิธี |
|---|---|
| บัตร | Stripe Checkout แบบ `subscription` ร้านละหนึ่ง Stripe customer (`shops.stripe_customer_id`) ใส่ `shop_id` ใน `client_reference_id` และ metadata |
| PromptPay | Stripe Checkout แบบ `payment` ครั้งละ 1 เดือน จ่ายสำเร็จแล้ว `paid_until = max(now, paid_until) + 1 เดือน` |
| อัปเกรด ลดแพ็กเกจ เปลี่ยนบัตร ยกเลิก | Stripe Customer Portal ตั้งให้สลับแพ็กเกจที่ขายได้ และยกเลิกได้ตอนสิ้นรอบ |

- ทุกงานเรื่องเงินทำได้เฉพาะเจ้าของ และต้อง login ภายใน 10 นาที
- server ดึง `price_id` จาก `plan_versions` เอง ไม่รับราคาหรือ price จาก client
- หน้า success แสดง "กำลังยืนยันการชำระเงิน" แล้วถาม `GET /api/v1/billing` ซ้ำทุก 2 วินาที นานสุด 60 วินาที **แพ็กเกจเปิดจาก webhook เท่านั้น**
- PromptPay แจ้งเตือนในแอป 7 วันก่อนหมดอายุ และส่งอีเมลถ้ามีอีเมล

### Webhook

- `POST /api/v1/stripe/webhook` ตรวจลายเซ็นจาก raw body ด้วย `stripe.webhooks.constructEventAsync` ยอมให้เวลาคลาดได้ 300 วินาที
- เก็บ `event.id` ใน `stripe_events` (ห้ามซ้ำ) event ที่เคยประมวลผลแล้วตอบ 200 ทันที
- ไม่เชื่อลำดับ event ทุกครั้งดึงสถานะ subscription หรือ checkout session ล่าสุดจาก Stripe API มาเขียนทับ
- event ที่รับ:
  - `checkout.session.completed`
  - `checkout.session.async_payment_succeeded` / `checkout.session.async_payment_failed`
  - `customer.subscription.created` / `updated` / `deleted`
  - `invoice.paid` / `invoice.payment_failed`
- ใช้ restricted API key ที่มีสิทธิ์เท่าที่ต้องใช้

### แพ็กเกจที่ใช้จริง

- ตาราง `subscriptions`: `shop_id`, `plan_version_id`, `source` (`card`, `promptpay`, `comp`), `status`, `period_end`, `cancel_at_period_end`, `stripe_subscription_id`
- แพ็กเกจที่ใช้จริง = แพ็กเกจของ subscription ถ้า `now <= period_end + 14 วัน` ไม่เช่นนั้นเป็น Free ระหว่าง 14 วันนี้ขึ้นแถบเตือนให้จ่ายทุกครั้งที่เปิดแอป
- Worker cache แพ็กเกจที่ใช้จริงต่อร้าน 60 วินาที และส่งเพดานไปกับทุกคำสั่งที่ส่งให้ Durable Object
- เตือนในแอปที่ 80% และ 100% ของแต่ละเพดาน
- **เกินเพดาน:** เพิ่มรายการชนิดที่เกินไม่ได้ ส่วนข้อมูลเดิมยังใช้ได้ (เกินเพดานบิลแล้วออกบิลใหม่ไม่ได้จนกว่าจะอัปเกรดหรือขึ้นเดือนใหม่ ยกเว้นตามส่วนที่ 3)
- **ลดแพ็กเกจหรือหมดอายุแล้วไม่ลบข้อมูล**
- นับบิลรายเดือนตามปฏิทินเขตเวลา Asia/Bangkok

### หลังบ้านทีม (`admin.`)

- อยู่หลัง Cloudflare Access บังคับ MFA และ Worker ตรวจ `Cf-Access-Jwt-Assertion` กับ public key ของ Access ทุก request
- ทำได้:
  - ค้นร้าน ดูแพ็กเกจและประวัติจ่ายเงิน
  - เปิดหรือต่อแพ็กเกจแบบ `comp`
  - สร้างและแก้ `plan_versions`
  - ระงับร้าน
  - ดู audit log
- **ทีมไม่เห็นข้อมูลขายของร้านโดยปกติ** ถ้าจำเป็นต้องเข้าดู ต้องกรอกเหตุผล ระบบบันทึก และแจ้งเจ้าของร้าน
- ทุกการกระทำในหลังบ้านบันทึก audit log พร้อมอีเมลของคนในทีม

## 5. Security, การดูแลระบบ, PDPA และเทสต์

### Header และหน้าเว็บ

- **CSP**
  - `default-src 'self'`
  - `script-src 'self'`
  - `style-src 'self'`
  - `img-src 'self' blob: data:`
  - `connect-src 'self'`
  - `font-src 'self'`
  - `frame-ancestors 'none'`
  - `base-uri 'none'`
  - `form-action 'self'`
- แก้ `style="..."` ในสตริง HTML 8 จุด (`app.js` 7 จุด, `settings.js` 1 จุด) ให้ตั้งค่าผ่าน `element.style` หลัง render แอปไม่มี inline script หรือ inline event handler อยู่แล้ว
- **header อื่น:**
  - `Strict-Transport-Security: max-age=63072000; includeSubDomains; preload`
  - `X-Content-Type-Options: nosniff`
  - `Referrer-Policy: strict-origin-when-cross-origin`
  - `Permissions-Policy` ปิดทุกอย่างยกเว้น `camera=(self)` สำหรับถ่ายรูปสินค้า
- ทุกจุดที่ใส่ข้อมูลลง `innerHTML` ต้องผ่าน `esc()`

### ตรวจข้อมูลและจำกัดความถี่

- ทุก endpoint และทุกชนิดคำสั่งมี schema กำหนดความยาวข้อความ ช่วงตัวเลข และจำนวนรายการ
- body ไม่เกิน 1 MB (ยกเว้นอัปโหลดรูป 5 MB)
- Workers Rate Limiting: ขอ OTP 5 ครั้ง/ชั่วโมงต่อปลายทาง และ 20 ครั้ง/ชั่วโมงต่อ IP, ยืนยัน OTP และ PIN ตามกฎล็อกในส่วนที่ 2, sync 60 ครั้ง/นาทีต่อเครื่อง, อัปโหลดรูป 60 ครั้ง/ชั่วโมงต่อร้าน
- เปิด WAF managed rules

### คีย์ สภาพแวดล้อม และ dependency

- environment `staging` กับ `production` แยก D1, R2, Queues, secret และบัญชี Stripe mode
- คีย์ทั้งหมดอยู่ใน `wrangler secret` CI รัน gitleaks ทุก PR
- token ของ Cloudflare ที่ CI ใช้มีสิทธิ์แค่ deploy Worker และ Pages ของโปรเจกต์นี้
- dependency ฝั่ง Worker มีแค่ `hono`, `stripe` และเครื่องมือเทสต์ ใช้ lockfile และเปิด Dependabot

### Log, การแจ้งเตือน และ backup

- log เป็น JSON ไม่เก็บ token, รหัส OTP, PIN, เบอร์โทร หรืออีเมลเต็ม (เก็บแบบปิดบางส่วน)
- ส่ง error เข้า Sentry โดยลบข้อมูลส่วนตัวก่อนส่ง
- **แจ้งเตือนเมื่อ:** error เกิน 1% ใน 5 นาที, webhook ล้มเหลว, ค่า SMS ถึง 80% ของเพดานวัน, อัตราคำสั่ง sync ที่ถูกปฏิเสธสูงผิดปกติ
- **backup:**
  - Durable Object และ D1 กู้ย้อนหลังได้ 30 วันในตัว
  - cron ส่งออกข้อมูลทุกร้านและ D1 ไป R2 `backups` ทุกวัน bucket lock 90 วัน
- **ซ้อมกู้ข้อมูลร้านทดสอบจาก backup จริงอย่างน้อย 1 ครั้งก่อนเปิดร้านนำร่อง**

### PDPA (ข้อกำหนดด้านเทคนิค ไม่ใช่คำปรึกษากฎหมาย)

- ตอนสมัครต้องยอมรับข้อตกลงและนโยบายความเป็นส่วนตัว บันทึกเวอร์ชันและเวลาใน `consents`
- เจ้าของส่งออกข้อมูลร้านเป็น JSON และ CSV ได้
- **ลบบัญชีหรือลบร้าน:** ซ่อนไว้ 30 วัน แล้ว cron ลบจริงทั้ง Durable Object (`deleteAll`), รูปใน R2 และแถวใน D1 ส่วน backup หมดอายุตามรอบ 90 วัน
- มีหน้ารายชื่อผู้ให้บริการที่ข้อมูลผ่าน: Cloudflare, Stripe, ผู้ส่ง SMS และอีเมล, LINE, Google, Sentry
- มีเอกสารขั้นตอนรับมือข้อมูลรั่ว เพื่อแจ้งภายใน 72 ชั่วโมง

### เทสต์

| กลุ่ม | ตรวจอะไร |
|---|---|
| คำสั่งใน Durable Object | ขาย เติม ยกเลิก จอง รับของ ปรับสต็อก เพดาน ตรวจราคา เวลาเพี้ยน เลขบิล (Vitest + `@cloudflare/vitest-pool-workers`) |
| แยกข้อมูลร้าน | session และ device token ของร้าน A เรียกทุก endpoint ด้วย id ของร้าน B แล้วต้องล้มเหลวทุกครั้ง และเทสต์สิทธิ์พนักงานกับทุกชนิดคำสั่งอัตโนมัติจากตารางสิทธิ์ |
| Sync | `op_id` ซ้ำ, ลำดับสลับ, ขายเกินสต็อกโหมดออนไลน์ถูกปฏิเสธ, ขายเกินสต็อกโหมดออฟไลน์ติดลบพร้อมธง, ตอบช้าเกิน 5 วินาทีแล้วเข้า outbox โดยไม่บันทึกซ้ำ, บิลพนักงานที่มีส่วนลดติดธง, cursor หมดอายุ, เครื่องถูกถอดแล้วล้างข้อมูล, มีคำสั่งค้างตอนถูกถอด |
| Auth | OTP หมดอายุและเกินจำนวนครั้ง, ข้อความตอบเหมือนกันทุกกรณี, ตรวจ Origin กัน CSRF, เปลี่ยน token ตอน login, งานสำคัญต้อง login ใหม่, ไม่รวมบัญชีตามอีเมล |
| Stripe | ลายเซ็นผิดได้ 400, event ซ้ำ, event มาไม่ตามลำดับ, PromptPay ยืนยันทีหลัง (Stripe CLI ใน test mode) |
| XSS | ใส่ payload ลงชื่อสินค้า ลูกค้า โน้ต และชื่อร้าน แล้วตรวจว่าไม่รัน |
| End-to-end | Playwright ปิดเน็ต → ขาย → เปิดเน็ต → ตรวจข้อมูลที่ server ต่อยอดจาก `verification/app-fixes.cjs` |
| ก่อน launch | ตรวจตาม OWASP ASVS ระดับ 2 และรัน `/security-review` ถ้ามีงบควรจ้าง pentest ภายนอก |

### CI/CD

- ทุก PR บน GitHub Actions: lint, typecheck, เทสต์ทั้งหมด, gitleaks
- merge เข้า `main` → deploy ขึ้น staging
- tag `v*` + อนุมัติใน GitHub Environment → deploy ขึ้น production
- ย้ายแลนดิ้งจาก Vercel มา Cloudflare และลบ `vercel.json` เมื่อย้ายเสร็จ

### ลำดับการเปิด

1. staging ให้ทีมใช้
2. ร้านนำร่อง ทีมเปิดแพ็กเกจแบบ `comp`
3. เปิดสาธารณะโดย `BILLING_ENABLED` ยังปิด
4. เปิดการเก็บเงินหลังบัญชี Stripe activate

### ลำดับลงมือ (สำหรับแผน)

1. โครงพื้นฐาน: โฟลเดอร์ `worker/`, `wrangler.toml` แยก env, schema D1, CI
2. Auth และ session
3. Durable Object `Shop` + API + แอปทำงานแบบออนไลน์ผ่าน `store.js`
4. Sync ตอนออฟไลน์ + service worker
5. ย้ายข้อมูลจาก localStorage
6. แพ็กเกจ เพดาน และหลังบ้าน
7. Stripe
8. Header, backup, PDPA และตรวจก่อน launch
